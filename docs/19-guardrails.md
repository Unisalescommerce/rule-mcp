### rule-process-cargo-release

| Rule                              | Label                                                  | What it rejects                                                                                                                                                                                                                                                                                                                                                                                                          | Also in                                           |
| --------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------- |
| `release-no-long-lived-token`     | No long-lived crates.io token in a release workflow    | crates.io supports Trusted Publishing: an OIDC exchange returns a token that expires in 30 minutes and the action that fetches it revokes it when the job ends. A workflow that still reads `CARGO_REGISTRY_TOKEN` from `secrets.` holds a credential that can publish any version of any crate its owner can reach, and it survives the release - which is the one thing the exchange removes.                          | -                                                 |
| `release-token-step-scoped`       | The publish token is written on the publish step       | cargo cannot perform the OIDC exchange itself - `cargo publish --help` has no token or OIDC flag - so the temporary credential is injected through the environment. Where it is written decides who can read it: on the publish step it exists for that one command, at job level every step inherits it, and at workflow level every job does. The exchange buys nothing if the token is then handed to a build script. | -                                                 |
| `release-actions-pinned`          | Every action is pinned to a commit SHA                 | A release workflow runs with privileges nothing else in the repository has, and a tag like `@v4` is a pointer its owner can move at any time without a diff here. Pinning the full SHA makes the update explicit and reviewable; the trailing version comment keeps it readable, so the pin is not a hex blob nobody dares touch.                                                                                        | rule-process-npm-release, rule-process-uv-release |

A job that also builds or fetches dependencies hands that power to every build script in the workspace - and a Rust workspace has a lot of them. One job, no toolchain install, no cache: the exchange and the publish, nothing else.                                                | rule-process-npm-release, rule-process-uv-release |
| `release-dry-run-first`           | A dry run runs before the upload                       | A publish is permanent: the version cannot be overwritten and the code cannot be deleted. `cargo publish --dry-run` (or `cargo package`, which is the same three steps) builds the archive, verifies it compiles and leaves it in `target/package`, so a crate that fails to package fails before the version exists. Without it, the first time anyone sees the contents is after the upload.                           | -                                                 |
| `release-package-list`            | The packed file list is inspected before the upload    | `cargo package --list` is the only view of what the `.crate` will contain, and it is the step people skip. | `release-manifest-metadata`       | The manifest carries the metadata crates.io requires   | crates.io refuses a first publish without `license` (or `license-file`), `description`, `repository` and `readme`, and it refuses it after the archive is built. The failure is cheap but it arrives at the worst moment, and the missing field is usually the one that makes a crate discoverable at all - which is the difference between a release and a release somebody can find.                                   | -                                                 |
| `release-version-not-in-workflow` | The version is not written in the workflow             | A version baked into a tag-triggered workflow is a second source of truth: the tag says one thing, the step writes another, and whichever lands second wins silently.
